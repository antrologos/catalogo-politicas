## Abordagem (6 sub-blocos)

### E.1 — Benchmark UX-first com lente "gestores públicos" (3 Explore agents)

**Agent E.1.A — Atlas Brasil PNUD + comparação inter-UF**
- Investiga em profundidade o fluxo de seleção múltipla (até N localidades + N indicadores) → tabela + mapa + gráfico
- Testa caminhos alternativos de comparação
- Output: especificação detalhada para o wireframe "Comparação inter-UF" do nosso catálogo (adaptado: comparar UFs em dimensões = tipo_politica, eixo, cobertura, situação)

**Agent E.1.B — gov.uk Design System + ObservaSampa para gestores públicos**
- Lê doc do gov.uk Design System (componentes, padrões, tom de voz) com lente "gestor público"
- Analisa ObservaSampa como exemplo brasileiro de dashboard executivo
- Output: como aplicar patterns gov.uk ao nosso site (componentes, tom, semântica)

**Agent E.1.C — Atlas Violência IPEA + dashboards por estado**
- Investiga como IPEA expõe "estado X" com KPIs + cortes demográficos + filtros + downloads
- Identifica o que adapta para "dashboard executivo de UF" do nosso catálogo
- Output: especificação detalhada dos wireframes #6 (página executiva por UF) e #1 (home/dashboard agregado)

**Checkpoint E.1**: consolidação dos 3 outputs + re-priorização dos 8 wireframes para gestores

### E.2 — Requisitos funcionais e não-funcionais (MoSCoW)

Síntese sem agents — feito direto via leitura do material consolidado + decisões. Lista priorizada:

- **Must have**: navegação por UF, busca facetada (por vocabulário canônico), ficha individual com snapshot integral linkado/embedado, comparação inter-UF (2-N políticas), exportação CSV/JSON, citação ABNT/APA/BibTeX, WCAG 2.2 AA, performance Core Web Vitals
- **Should have**: mapa coroplético interativo, dashboard executivo por UF, página "como adotar" para gestores
- **Could have**: timeline cronológica, visualização em rede de relações, sumário em PDF gerado por requisição
- **Won't have (Bloco G)**: cadastro de usuário, alertas por email/RSS, API REST/GraphQL, editor colaborativo, scoring de qualidade automatizado

ADR `2026-05-XX_requisitos-mvp.md` consolida.

### E.3 — Decisão de stack (3 Plan agents defendem 3 opções, ADR final)

**Agent E.3.A — Astro + Tailwind + Pagefind + ilhas React/Vue**
- Defende: site é majoritariamente conteúdo (navegação + leitura); build estático = deploy gratuito (Vercel/Netlify/GitHub Pages); Pagefind nativo para busca full-text de 148 snapshots; ilhas React/Vue para componentes interativos (mapa, comparação); i18n estruturado nativo no Astro; Core Web Vitals excelentes
- Custo de manutenção, learning curve, ecossistema, futuro 5 anos

**Agent E.3.B — Next.js + Tailwind + Algolia/MeiliSearch**
- Defende: mainstream React; SSR/ISR para SEO + dinâmica; route handlers para API se MVP virar app dinâmico; Algolia/MeiliSearch para busca avançada
- Pondera: complexidade adicional vale só se MVP virar app dinâmico depois

**Agent E.3.C — Quarto / Eleventy (mais minimalista)**
- Defende: máxima simplicidade; deploy trivial; sem JS (ou JS mínimo via plugins); custo zero de manutenção; perfil acadêmico forte (Quarto)
- Pondera: limita interatividade; comparação dinâmica precisa workarounds

**Checkpoint E.3**: usuária decide via AskUserQuestion (4 opções: cada stack + customizar). ADR `2026-05-XX_decisao-stack.md` registrada.

**Sub-decisão paralela**: hospedagem (Vercel free / Netlify free / GitHub Pages / IESP-UERJ servidor) — geralmente acoplada à stack.

### E.4 — Wireframes (8 prioritizados, adaptados para gestores)

8 wireframes em ASCII art ou HTML semântico simples (sem CSS/JS — só estrutura + anotações):

1. **Home / Dashboard de cobertura por UF** — entrada do gestor; mostra "439 políticas | 9 UFs + Federal | mapa Brasil clicável | últimas atualizações | top 5 fichas em destaque"
2. **Mapa coroplético** — Brasil → estado → ficha (UF é centro do drill-down)
3. **Comparação inter-UF** — selecionar 2-N UFs → tabela comparativa por eixo + tipo + cobertura
4. **Ficha individual** — cabeçalho com IDs/datas/citação + bloco "executado em N estados; ver onde" + texto integral embedado (snapshot) + relações (replica de federal X) + botão exportar
5. **Busca facetada** — sidebar com vocabulário canônico (eixo, esfera, modalidade, tipo, situação) + contador ao vivo por faceta + cards estilo data.gouv.fr com badge de completude
6. **NOVO: Página executiva por UF** — dashboard de uma UF: N políticas ativas, M federais replicadas, top eixos, links rápidos para cada uma, botão "exportar resumo executivo PDF"
7. **NOVO: Página "Como adotar uma política?"** — playbook prático para gestor: passos, normas-base, exemplos de outras UFs que já adotaram, contatos institucionais
8. **Como citar / Sobre os dados** — transparência metodológica: versão do catálogo, equipe, contato, licença CC, link para repo aberto

Saída: `docs/wireframes/<n>-<nome>.html` ou `docs/wireframes/<n>-<nome>.md` (ASCII art).

### E.5 — Sistema de design enxuto

- Tokens: cores (3-5 cores semânticas), tipografia (1-2 famílias web-safe), espaçamento (escala 4/8/16/24/32), breakpoints (320/768/1024/1440)
- Componentes mínimos: Card, Tag, Filter, Search, Compare, Citation, Footer, Nav, Button, Badge
- Inspiração principal: gov.uk Design System (semântico, sóbrio, executivo)
- Identidade visual: usar tons institucionais FRM/IESP-UERJ se existirem (decisão sub-checkpoint humano)
- Output: `docs/design-system.md` (tokens + componentes; pode ser CSS variables ou config Tailwind dependendo de E.3)

## Riscos e mitigações

- **Risco**: identidade visual FRM/IESP não existir → criar do zero adiciona complexidade ao E.5 → **mitigação**: aceitar paleta neutra inspirada em gov.uk como default; refinamento estético fica para iteração pós-MVP
- **Risco**: stack escolhida não suportar todos os requisitos do E.2 → **mitigação**: argumentação dos 3 agents do E.3 obriga checagem requisito-a-requisito; ADR documenta trade-offs
- **Risco**: 8 wireframes virarem só esqueleto sem alma → **mitigação**: cada wireframe tem anotações sobre dados consumidos do JSON e fluxo de uso; revisão humana antes de E.5
- **Risco**: Bloco E ficar grande demais → **mitigação**: cada sub-bloco tem entregável próprio; checkpoint após E.1 e E.3 antes de continuar
- **Risco**: pendências (identidade, hospedagem, manutenção) ficarem soltas → **mitigação**: cada uma tem sub-checkpoint dedicado em E.5/E.3/E.6 respectivamente
- **Risco**: usuária aprovar wireframes mas mudar de ideia em Bloco F → aceitável, parte do processo iterativo; ADRs facilitam revisão
