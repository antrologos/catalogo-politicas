## Lente 1 — Custos escondidos das recomendações R1.2

### Sobre Padrão #1 — Mosaico de eixos temáticos no topo de `/explorar/` (referência: 1.2 linha 176)
- **Crítica**: estimado "M (precisa derivar tags por heurística)" — mas 439 fichas heterogêneas, eixos sobrepostos (PRONATEC é "qualificação" e potencialmente "EJA quando turma é EJA"; Bolsa Família é "transferência condicionada" e potencialmente "inclusão produtiva"). Heurística sobre nome+resumo vai cair em 10-20%, exigindo override manual. Sem ferramenta de revisão (admin UI), o override vira edição direta de JSON canônico — viola regra de paths protegidos (`policies-schema.json`, `data/derived/*.json`).
- **Solução proposta**: adicionar campo opcional `eixos_tematicos: ["eja"|"qualificacao"|"inclusao_produtiva"|"transferencia_condicionada"]` (multi-valor) no schema v0.3. Heurística inicial preenche; revisão humana é arquivo `data/curadoria/eixos_overrides.csv` (id,eixos) lido pelo ETL. Sem admin UI no MVP.
- **Quem implementa**: mantenedor solo até a heurística + 2-3h de revisão pontual de duplicatas óbvias. Curadoria sistemática (439 fichas × revisão) — espera bolsista. Decisão honesta: lançar M1 com tag derivada heurística + nota visível "tagging em revisão".

## Lente 2 — Pontos cegos não cobertos

### Ponto cego: Mobile real
- **Evidência**: nenhum dos 3 documentos cita "testado em iOS/Android"; auditorias falam em "viewport curto, notebook 13" landscape" (R1.1-A) — desktop. Cards `bg-primary p-md` em mobile + header sticky `py-md` + tags grandes nos H1 = primeira dobra mobile pode ter 0 conteúdo útil.
- **Impacto estimado**: persona primária (técnico estadual) provavelmente usa celular em campo. Se Home mobile mostra só hero + 1 card, abandono é alto.
- **Solução**: adicionar skill `.claude/skills/auditar-mobile/SKILL.md` (Playwright headless em viewports 375x667 e 414x896 com screenshot diff vs. desktop) — roda no CI antes de merge. Para o MVP: conferir 5 páginas-chave em DevTools mobile + 1 device real. Esforço: 2h skill + 4h auditoria = 6h.

### Ponto cego: Performance percebida em 3G
- **Evidência**: Pagefind index para 439 fichas pode chegar a 2-5MB em fragmentos. Em 3G real (1.6 Mbps), primeiro resultado de busca pode demorar 8-15s. Ninguém mediu.
- **Impacto estimado**: pesquisador no celular sai antes de o resultado aparecer; SEO interno (Pagefind) vira inviável para mobile.
- **Solução**: rodar Lighthouse mobile com throttle 3G nas 5 rotas-chave; documentar números em `.claude/working/E5-design-system.md`. Se >5s First Contentful Search, considerar hybrid: SSR de top-50 termos comuns + Pagefind para o resto. Esforço: 3h medição + decisão.

### Ponto cego: NVDA/TalkBack reais (axe não pega tudo)
- **Evidência**: pa11y-ci roda axe-core, mas ARIA tabs (`tabs.njk`), `aria-pressed` (proposto), `role=tablist` precisam validação com leitor de tela real. Axe valida estrutura, não comportamento.
- **Impacto estimado**: usuário com NVDA pode não conseguir navegar entre as 5 tabs da ficha; "Como citar" inacessível.
- **Solução**: 1 sessão de 2h com NVDA portátil em Windows + checklist específico (foco visível, anúncio correto de tab selecionada, ordem de leitura de KPIs). Documentar em `.claude/working/E5-a11y-screen-reader.md`. Repetir antes de M1.

### Ponto cego: Print stylesheet
- **Evidência**: grep retornou 0 ocorrências de `@media print` em `src/`. Pesquisador imprimindo ficha para reunião vai imprimir o header sticky azul, footer com 4 colunas e logos, tabs colapsadas (só a ativa imprime).
- **Impacto estimado**: persona secundária quer levar a ficha PDF para reunião. Sem print, exporta tela ruim ou não usa o site.
- **Solução**: adicionar `@media print` em `tailwind.css` que: (1) esconde header/footer/sidebar/CTAs; (2) força todas as tabs visíveis empilhadas; (3) inclui URL e data de captura no rodapé via CSS. Esforço: 3-4h.

### Ponto cego: Dark mode
- **Evidência**: 0 ocorrências de `prefers-color-scheme`. Tailwind config não tem variantes `dark:`.
- **Impacto estimado**: técnico em escritório com luz baixa, pesquisador noturno — desconforto. Não é bloqueante, mas público técnico-acadêmico espera.
- **Solução**: NÃO implementar no MVP. Adicionar nota em ADR: "dark mode adiado para onda 2; tokens semânticos (`bg-neutral-100` etc.) já permitem migração futura sem refactor profundo." Documentar como dívida técnica conhecida.

### Ponto cego: Persistência de estado entre sessões
- **Evidência**: filtros aplicados em `/comparacao/` ficam em URL (bom para bookmark) mas filtros internos das páginas de UF (situação/tipo/modalidade) provavelmente não vão à URL — verificar.
- **Impacto estimado**: técnico aplica 3 filtros em `/uf/sp/`, fecha, volta amanhã, perdeu tudo.
- **Solução**: padronizar URL state em todos os filtros internos via `?filtros=situacao=ativa,tipo=educacional`. Reusar mesmo helper JS de `/comparacao/`. Esforço: 6-8h. Não bloqueante M1.

### Ponto cego: Idioma — só PT-BR
- **Evidência**: nenhuma menção a EN. Pesquisador estrangeiro (LATAM, Portugal, EU) que estuda EJA/qualificação fica fora.
- **Impacto estimado**: público acadêmico internacional perdido. Citação ABNT/APA/RIS não compensa se o conteúdo é opaco.
- **Solução**: NÃO traduzir 439 fichas (impossível solo). Mas adicionar `<title>`, `<meta description>`, `og:title` em EN para a Home + `/sobre/` + página `/about-en/` curta (1 página descrevendo o catálogo, eixos, metodologia, link para citar). Esforço: 4-6h. SEO internacional decuplica, custo é mínimo.

### Ponto cego: Versionamento de ficha
- **Evidência**: schema tem `situacao_atual` mas histórico de mudanças (política Ativa em 2014, Suspensa em 2020, Descontinuada em 2024) não tem campo nem UI.
- **Impacto estimado**: pesquisador citando "PRONATEC: Ativa" em 2026 — quando virar Suspensa, citação fica errada. Sem snapshot da ficha por data, irreproduzível.
- **Solução**: adicionar `data_consulta` no `citation-box.njk` (já existe?) + documentar em `/sobre/` que a ficha reflete estado em [data_atualizacao]. Para histórico real: link para o snapshot externo capturado (já temos `data/external_snapshots/`) com data de captura. Esforço: 2h se já temos snapshot navegável da ficha.

### Ponto cego: Onboarding 1ª visita
- **Evidência**: nada de tour, hints, "comece por aqui". R1.1-B-J3 (gestor curioso) explicitamente quebra por isso.
- **Impacto estimado**: gestor curioso (persona terciária) é exatamente o caso "1ª visita" — abandona se não entende.
- **Solução**: NÃO implementar tour interativo (overengineering). Adicionar à Home, abaixo do hero, uma faixa textual única "Comece por: 1) [Buscar tema X] 2) [Ver UF] 3) [Comparar 2 UFs]" com 3 links âncora — funciona como onboarding sem JS, ~10 linhas Njk, ~1h.

### Ponto cego: Feedback de erro inconsistente
- **Evidência**: link "Encontrou erro?" provavelmente está só na ficha (R1.1-B menciona). UFs/dimensões/busca não têm.
- **Impacto estimado**: erro em listagem agregada (ex.: contagem errada na UF) não tem canal — usuário não reporta.
- **Solução**: adicionar componente `_includes/components/feedback-link.njk` com `mailto:` ou link para issue do GitHub pré-preenchido com URL atual. Inserir no footer de TODAS as páginas. Esforço: 2h.

## Lente 4 — Riscos sistêmicos

### Risco: Bolsista não vier após 2026-07-01 → MVP enterrável
- **Probabilidade × impacto**: probabilidade média (cláusula reabertura existe por algo); impacto alto se materializar (480-1070h solo = 2.5-5.5 anos).
- **Solução/mitigação**: na arquitetura do MVP, priorizar features que **sobrevivem sem manutenção** (busca, fichas estáticas, citações) e adiar features que **exigem curadoria contínua** (eixos temáticos com override manual; mapa colorido por dimensão que muda com onda nova). Documentar em `.claude/decisions/2026-05-01_priorizacao-features-resilientes.md` quais features são "pousáveis" e quais "exigem manutenção".

### Risco: Credibilidade institucional FRM/IESP/Bradesco
- **Probabilidade × impacto**: alta probabilidade de erros visíveis em qualquer site; impacto alto (rede acadêmica nota e cita).
- **Erros mais danosos para credibilidade hoje**:
  1. **Duplicata BA visível** (R1.1-B-Crítico) — público técnico que conhece BA pensa "se erra isso, erra outras coisas".
  2. **`/comparacao/` que não compara** — pesquisador acadêmico julga em 30s.
  3. **"Federal Federal (Brasil)" no H1** (R1.1-A-Crítico-2) — erro de polimento que vira screenshot de Twitter.
- **Solução/mitigação**: tratar os 3 acima como bloqueantes de M1 (beta para 2-3 gestores). Adicionar checklist "credibilidade" ao roteiro de release: 5 erros de polimento que ESTRAGAM impressão (digitar errado nome de UF, contagem inconsistente entre Home/UF/dimensão, link quebrado em política federal canônica, screenshot do site no `/sobre/` desatualizada, footer dizendo "PoC" depois do lançamento oficial).

### Risco: LGPD invisível — Pagefind + GitHub Pages logs
- **Probabilidade × impacto**: probabilidade alta de inquérito hipotético; impacto médio (multa improvável dado o porte, mas embaraçoso para FRM/IESP).
- **Evidência**: site não tem analytics próprio (verificado), mas: (1) GitHub Pages registra IP + UA; (2) Pagefind faz fetch de fragmentos JSON do mesmo domínio (não é tracking, mas é processamento de comportamento de busca); (3) link "Reportar erro" provavelmente envia para GitHub Issues (público).
- **Solução/mitigação**: revisar `/sobre/privacidade.md` (existe!) para mencionar explicitamente: (a) hospedagem GitHub Pages + sua política; (b) Pagefind é client-side, sem servidor próprio; (c) uso do GitHub Issues para feedback (público, com IP via login). Linkar no footer de TODAS as páginas (não só /sobre/). Esforço: 2h.

### Risco: Drift de dados na onda 2
- **Probabilidade × impacto**: alta probabilidade (já há 31 valores únicos de `esfera_execucao` para 20 oficiais); impacto médio.
- **Solução/mitigação**: cada componente UI que renderiza valor categórico deve ter fallback "—" ou "Outro" para valor desconhecido (não throw). Adicionar teste em `tests/toy_render_categorias.py` que injeta valor fora do vocabulário e valida render gracioso. Documentar em ADR a contrato "UI fail-soft em drift".

### Risco: SEO — pesquisador não acha ficha via Google
- **Probabilidade × impacto**: alta probabilidade de baixa indexação inicial (site novo); impacto alto (perde a entrada lateral J5).
- **Evidência**: não verifiquei meta tags atuais. Slugs longos são bom para SEO (R1.1-B). Mas: schema.org `Dataset` ou `GovernmentService` provavelmente ausente. `og:image` por ficha? Sitemap.xml gerado pelo Eleventy?
