# Pesquisa 2.2 — Boas Práticas Estendidas (revisão pós-R2.1)

**Foco**: validar/refinar propostas de R2.1-A (beleza) e R2.1-B (facilidade) com fontes externas que **não** se sobrepõem a R1.2.
**Data**: 2026-05-01
**Mandato**: estender, não repetir. Cada exemplo desta rodada é diferente daqueles citados em R1.2 (data.gov.uk, gov.uk Tag/Topic, USWDS Tag, EUR-Lex, NIS2 Tracker, gov.uk Publishing Related Nav, Wikipedia See Also, Semantic Scholar, OECD CYC, Atlas Brasil PNUD, World Bank DataBank, Material Design 3, GOV.BR DS) — quando uma URL aparece, é com ângulo distinto.
**Fontes consultadas**: 16 (12 com conteúdo aproveitável via WebFetch + WebSearch). Cinco URLs falharam (`gov.br/ds/home` retorna só título; `nexojornal`, `atlasbrasil`, `dadosabertos.gov.br`, `oramasearch`, `cidades.ibge`, `design.gov.au` retornaram ECONNREFUSED ou conteúdo magro). Suprido com cruzamento de buscas e referências secundárias.

---

## Resumo executivo

1. **Não existe "paleta brasileira institucional + editorial moderna" canônica.** A própria identidade `gov.br` mistura azul-atlântico `#183EFF` com Rawline (fonte). Cada projeto sério inventa a sua paleta — IBGE/Atlas/Fiocruz/Datafolha não convergem. Isto **valida** a Opção A da R2.1-A (azul-IBGE + verde-floresta + sienna + papel) como invenção legítima, mas **refina**: documentar a paleta como decisão editorial autoral (não "padrão BR"), porque não há padrão.
2. **IBM Plex está confirmado como escolha sólida** — Wikipedia + GitHub IBM/plex + Adobe Fonts + Google Fonts confirmam: SIL OFL 1.1, 4 variantes (Sans, Serif, Mono, Sans Condensed), 100+ idiomas Latin estendido (português coberto), variável só em Sans (até abr/2019; o restante é estático multi-peso). IBM trocou Helvetica por Plex em 2017 — fonte específica deste projeto, **não-genérica em catálogos brasileiros**. Refinamento à R2.1-A: para body, **considere também `Inter` ou `Public Sans`** se houver risco de "Plex em todo lugar" (já é fonte de várias dashboards técnicas).
3. **Pagefind 1.5.2 (versão atual abr/2026) NÃO oferece fuzzy nativo, NÃO oferece sinônimos nativos**, mas oferece (a) stemming português automático via `<html lang="pt-br">`, (b) `data-pagefind-meta` para enriquecer metadados, (c) Component UI customizável. **Refina R2.1-B**: a proposta "Pagefind com fuzzy + sinônimos" precisa **camada de aplicação** (sinônimos via `data-pagefind-meta`, "Quis dizer" via componente próprio, fuzzy via fallback Lunr.js — caminho ADR-008). Não troque de engine.
4. **Zotero connector reconhece Highwire Press (`citation_*`) como padrão de fato** para extração automática. 5 meta tags resolvem 80% do caso: `citation_title`, `citation_author`, `citation_publication_date`, `citation_publisher`, `citation_doi`. Para catálogo de políticas, item type Zotero é **`Report`** ou **`Document`**. **Valida R2.1-B (export RIS/BibTeX)**: a infraestrutura do site permite "Zotero detecta automaticamente" sem botão extra, ANTES mesmo de implementar export em batch.
5. **Onboarding e glossário não são canônicos em catálogos públicos** — gov.uk DS não tem tour, Datawrapper Academy é wiki por categoria, IBGE Cidades não tem onboarding visível. **Refina R2.1-B (glossário + FAQ + onboarding)**: a recomendação é correta mas é diferenciador, não compliance — vale priorizar **glossário inline (tooltip)** sobre tour Shepherd.js (que é overkill para 8 wireframes).
6. **Phosphor Icons (MIT, 6 pesos, ~9k ícones) é escolha defensável**, mas com pegadinha: bundle completo ~3MB. **Refina R2.1-A**: usar **eleventy-plugin-phosphoricons** (já existe community plugin) para inline SVG sob demanda — não webfont. **Lucide (ISC, 1703 ícones, tree-shakable nativo)** é alternativa mais leve se peso editorial não for prioritário.
7. **Identidade brasileira sem clichê = NÃO usar verde-amarelo-azul juntos**. As 3 melhores referências (Fiocruz: 5 painéis temáticos institucionais; IBGE Cidades: navegação modular por dimensão; gov.br: azul + Rawline) usam **um eixo cromático principal** + acentos sóbrios. Valida Opção A da R2.1-A.

## Tema 1 — Paletas editoriais brasileiras

**Pergunta-mãe**: existe "paleta brasileira institucional+editorial moderna" canônica?
**Resposta verificada**: **NÃO**. Cada projeto sério inventa a sua. A invenção da R2.1-A é legítima — mas precisa documentar isso explicitamente, sob pena de parecer cópia.

### Exemplo 1.1 — Identidade Visual gov.br oficial (cor + fonte Rawline)
**URL**: https://barra.governoeletronico.gov.br/atualize.html (verificado, conteúdo magro) + WebSearch agregada.
**Padrão observado**: a marca gov.br pós-2023 usa **`#183EFF` (azul-atlântico)** como cor primária + **Rawline** (fonte sans-serif livre) — distância significativa do `#0066cc` gov.uk-puro do MVP atual. O barramento federal injeta CSS próprio em sites que usam a "barra de identidade", forçando contraste com cinzas neutros.
**Aplicabilidade**: **PARCIAL** — gov.br é referência institucional, mas usar `#183EFF` puro daria "site federal" (não é o caso: catálogo é FRM/IESP, organizações independentes). Usar Rawline também colaria com sites federais — **R2.1-A acerta em escolher azul-IBGE (`#1A4F8B`) que é mais sóbrio + IBM Plex que é internacional.**
**Como adaptar**: documentar em ADR de design "**escolhemos não usar paleta gov.br para preservar independência editorial**" — argumento defensável e enxuto.

### Exemplo 1.2 — Observatório Fiocruz (5 painéis + alto contraste opcional)
**URL**: https://observatorio.fiocruz.br/ (verificado).
**Padrão observado**: organização em **5 painéis temáticos institucionais** (Pesquisa · Educação · Desenvolvimento Tecnológico · Relações Internacionais · Administração), cada um com cor própria sutil + ícone vetorial. Footer com logo Fiocruz + SUS + Governo Federal — **carimbo institucional explícito**. Recursos de a11y: alto contraste, cores invertidas, A-/A+. Cores reais não foram extraíveis (CSS dinâmico), mas o padrão é **verde-floresta + cinzas mornos + acento institucional Fiocruz**.
**Aplicabilidade**: **SIM**. Modelo direto para "catálogo BR institucional sério":
- Adotar 5-7 painéis temáticos com 1 cor sutil cada (não 7 cores cheias) — confirma A-Importante de R1.1-A e refina R2.1-A (ritmo cromático restrito).
- **Selo institucional explícito no footer** (FRM + IESP + Bradesco + parceiros) é canônico em catálogo público brasileiro — refuta a ideia da R2.1-A de "logo no header" como obrigatório, mas confirma a necessidade de identidade institucional visível.
**Como adaptar**: **footer institucional rico** (logos + missão curta) em vez de header carregado.

### Exemplo 1.3 — IBGE Cidades e Estados (paleta institucional + ícones modulares)
**URL**: https://www.ibge.gov.br/cidades-e-estados.html (verificado parcialmente — CSS embutido não-extraível).
**Padrão observado**: navegação modular por dimensão (Área Territorial, População, Educação, Emprego), **cards uniformes com ícone + número grande + label**, paleta dominada por **azul institucional IBGE + cinza neutro**. Sem cards coloridos competindo. Export em XLSX/XLS/ODS/CSV embutido. Modo alto contraste.
**Aplicabilidade**: **SIM**. Reforça três pontos: (a) cards uniformes com ícone + número (padrão "fact module" — também observado no USWDS Card de R1.2, mas IBGE adapta para PT-BR); (b) export em formatos múltiplos é canônico — adicionar à R2.1-B (export RIS/BibTeX **+** CSV/XLSX); (c) azul institucional sólido **valida** `#1A4F8B` da R2.1-A.
**Como adaptar**: módulos KPI no estilo IBGE Cidades — `[ÍCONE] [NÚMERO GRANDE] [LABEL CURTO]` em uma única cor (a primária), sem cards coloridos.

### Conclusão Tema 1
- **Paleta brasileira canônica não existe** — cada projeto institucional sério inventa, ancorando em 1 cor primária + cinzas + 1 acento. Sienna/coral nunca apareceu nas 3 referências BR; é sua invenção autoral — defensível mas precisa ADR.
- **Identidade BR sem clichê** = **um eixo cromático + footer institucional + tipografia sóbria**. Verde-amarelo-azul juntos é folklórico (Atlas Brasil PNUD usa, Fiocruz não, IBGE não, gov.br novo não).

## Tema 2 — Tipografia para catálogos sérios em PT-BR

### Exemplo 2.1 — IBM Plex (Wikipedia, GitHub IBM/plex, IBM Design Language)
**URLs**: https://en.wikipedia.org/wiki/IBM_Plex + https://github.com/IBM/plex + https://www.ibm.com/design/language/typography/typeface/ (todos verificados parcialmente; o ibm.com retornou 403 mas Wikipedia + GitHub confirmaram).
**Padrão observado**:
- **Família**: Sans, Serif, Mono, Sans Condensed.
- **Pesos**: 8 por variante + true italics.
- **Variável**: **só** Sans tem variable font (abr/2019). Serif e Mono ainda são estáticas multi-peso (~10-15kb por peso woff2).
- **Licença**: SIL OFL 1.1 — uso comercial livre, redistribuição livre, modificação livre.
- **Idiomas**: 100+ Latin estendido — português incluso com diacríticos completos (verificado por GitHub releases).
- **Adoção institucional**: IBM (corporativa, substituiu Helvetica em 2017), MIT Press blog, GitLab Pages (em algumas docs), Carnegie Foundation. **Não é cliché em Brasil** — vi raríssimo uso em sites públicos brasileiros.
**Aplicabilidade**: **SIM, valida R2.1-A**. Recomendação está correta. Refinamento:
- Carregar **só Plex Sans Variable + Plex Serif 400/600 + Plex Mono 400** = ~80kb total woff2 self-hosted. Suficiente.
- **Não carregar Sans Condensed** — não há uso justificado.
**Como adaptar**: configuração CSS:
```css
@font-face { font-family: "IBM Plex Sans"; src: url("/fonts/IBMPlexSans-Var.woff2") format("woff2-variations"); font-weight: 100 700; font-display: swap; }
@font-face { font-family: "IBM Plex Serif"; src: url("/fonts/IBMPlexSerif-Regular.woff2") format("woff2"); font-weight: 400; font-display: swap; }
@font-face { font-family: "IBM Plex Serif"; src: url("/fonts/IBMPlexSerif-SemiBold.woff2") format("woff2"); font-weight: 600; font-display: swap; }
@font-face { font-family: "IBM Plex Mono"; src: url("/fonts/IBMPlexMono-Regular.woff2") format("woff2"); font-weight: 400; font-display: swap; }
```

### Exemplo 2.2 — Public Sans (USWDS) e Inter (alternativas defensáveis)
**URLs**: implícito de R1.2 (USWDS usa Public Sans) + WebSearch sobre IBM Plex que listou Adobe Fonts (onde Inter também aparece).
**Padrão observado**:
- **Public Sans**: USWDS, baseada em Libre Franklin, gov-friendly, neutra. Ótima para "vista de governo amigável", mas pode parecer "demasiado USWDS" — colaria estética com governo americano.
- **Inter** (Rasmus Andersson): padrão SaaS moderno (Vercel, Linear, OpenAI docs). Variable nativo, ótimo para mobile, mas **muito comum** — em 2026 começa a parecer "fonte default Vite/Next".
- **Geist** (Vercel 2024): bonita, moderna, mas brand Vercel — risco de "site Vercel".
**Aplicabilidade**: **PARCIAL — Plex segue melhor para catálogo brasileiro** porque (a) é internacional sem ser americano, (b) Plex Serif é uma das melhores serif livres para body (não só display).
**Refinamento à R2.1-A**: rejeitar Inter como primeiro candidato. Plex é a escolha certa.

### Conclusão Tema 2
- **IBM Plex Sans + Plex Serif + Plex Mono = decisão validada** com fontes confirmadas. ~80kb total self-hosted.
- **Risco**: Plex está crescendo em adoção; em 3-4 anos pode virar "novo Inter". Mitigação: usar **Plex Serif para H1/destaque** (que é menos comum que Plex Sans) — assina identidade autoral.

## Tema 3 — Catálogos organizados por modelo mental do USUÁRIO

### Exemplo 3.1 — Observatório Fiocruz (5 painéis institucionais como modelo mental)
**URL**: https://observatorio.fiocruz.br/ (verificado).
**Padrão observado**: navegação por **eixos da própria atividade institucional** (Pesquisa, Educação, etc.) — não por **dimensões administrativas**. O usuário navega pela **função** que quer monitorar, não pelo "tipo de instrumento".
**Aplicabilidade**: **SIM, valida R2.1-B (reorganizar IA pelo modelo mental)**. Confirma: "eixos temáticos do problema do usuário > dimensões da planilha-fonte". Modelo Fiocruz é **3-7 eixos no topo**, dimensões adm como filtro secundário. Exatamente o que R1.1-B-Crítico-1 e R2.1-B-H1 propõem.

### Exemplo 3.2 — IBGE Cidades (modular por dimensão temática, não por unidade administrativa)
**URL**: https://www.ibge.gov.br/cidades-e-estados.html (verificado parcialmente).
**Padrão observado**: o usuário entra por **município** e dentro do município vê **dimensões** (Área, População, Educação, Emprego, PIB). A navegação é dupla — UF/município no eixo geográfico, dimensão no eixo temático. Cada dimensão tem ícone + valor + opção "ver mais".

- **Eixo geográfico** (UF + Federal) — já existe, OK.
- **Eixo temático** (4 eixos do projeto: EJA, Qualificação, Inclusão Produtiva, Transferência Condicionada) — falta criar.

A página `/explorar/` deveria ter **3 colunas/cards de entrada paralelos** (Por geografia · Por eixo temático · Por dimensão administrativa), não as 7 dimensões alinhadas como hoje.

### Exemplo 3.3 — gov.uk DS Get Started (curadoria editorial humana, não algoritmo)
**URL**: https://design-system.service.gov.uk/get-started/ (verificado).
**Padrão observado**: o GOV.UK DS oferece dois caminhos curados (**Prototyping** vs **Production**) na entrada, depois subdivide em "How to" guides. Cada caminho é **uma persona explícita** (designer iniciando vs equipe em produção). **Não é algoritmo, é editorial**.
**Aplicabilidade**: **SIM, refina R2.1-B**. A reorganização por modelo mental deve ser **curadoria humana** (editorial), não derivação automática por heurística sobre nome/resumo. Sustenta:
- Definir **manualmente** qual eixo temático cada uma das 439 fichas pertence (campo CSV override, ~3-5h de curadoria).
- Não confiar em "heurística sobre texto" como propõe R1.1-B-Crítico-1 (R2.1-B já cita isso como "frágil, 30-40% erro").

### Conclusão Tema 3
- **Reorganização por modelo mental do usuário é prática validada** em catálogos públicos sérios (Fiocruz, IBGE).
- **Curadoria humana > heurística automática** para classificar 439 itens em 4 eixos.
- A página `/explorar/` precisa **3 entradas paralelas** (geografia · tema · dimensão), não 7 dimensões alinhadas — confirma R2.1-B-H1.

## Tema 4 — Busca semântica + fuzzy em sites estáticos

### Exemplo 4.1 — Pagefind 1.5.2 oficial (sem fuzzy, sem sinônimos nativos)
**URLs verificadas**: https://pagefind.app/docs/multilingual/ + https://pagefind.app/docs/search-config/ + https://pagefind.app/docs/config-options/ + https://github.com/CloudCannon/pagefind.
**Padrão observado**:
- **Versão atual**: v1.5.2 (12-abr-2026), Rust 69%, mantida ativamente.
- **Stemming**: automático para o idioma do `<html lang="...">`. Para `<html lang="pt-br">`, Pagefind aplica stemmer Snowball para português — ou seja, "qualificação" e "qualificado" colapsam no mesmo token. **Funciona out-of-the-box**.
- **Fuzzy / typo tolerance**: **NÃO TEM** nativamente. Não há opção `fuzzy: true` em search-config. Confirmado pelas 3 páginas de docs verificadas.
- **Sinônimos**: **NÃO TEM** nativamente. Sem `synonyms.json`. Único caminho é via `data-pagefind-meta` (enriquecer cada ficha com aliases) ou meta `keywords` indexada.
- **Diacríticos**: opção `Exact Diacritics` permite tratar "ção" diferente de "cao" — útil para PT-BR.
- **Component UI** (1.5.0+): customizável; permite componente próprio para zero-result.
**Aplicabilidade**: **REFINA R2.1-B substancialmente**. A proposta "Pagefind com fuzzy + sinônimos" é **incorreta tecnicamente** — Pagefind NÃO oferece. Caminhos defensáveis:
1. **Fuzzy via fallback**: já está no ADR-008 (Pagefind→Lunr). Usar Lunr.js client-side **só** quando Pagefind retorna 0. Lunr suporta `~1` (Damerau-Levenshtein distância 1) para typo tolerance básica.
2. **Sinônimos via `data-pagefind-meta`**: para cada ficha, adicionar:
   ```html
   <div data-pagefind-meta="aliases:EJA, Educação de Jovens e Adultos, ensino para adultos, supletivo, alfabetização adulto"></div>
   ```
   Pagefind indexa esse meta como texto buscável. Custo: ~3h de curadoria sobre vocabulário canônico.
3. **"Quis dizer" via componente próprio**: na zero-result (Component UI), comparar query com lista de termos populares + string-distance < 3, sugerir.
**Como adaptar**:
- Manter Pagefind como engine primária.
- Adicionar Lunr.js (32kb) como fallback cliente.
- Curadoria de 50-100 sinônimos populares no `data-pagefind-meta`.
- Componente "zero-result" próprio com sugestões + tag-cloud.

### Exemplo 4.2 — Algolia "Fuzzy Search 101" (Damerau-Levenshtein como padrão de fato)
**URL**: https://www.algolia.com/blog/engineering/fuzzy-search-101 (verificado).
**Padrão observado**: o algoritmo dominante é **Damerau-Levenshtein** (substitui, insere, deleta, transpõe). Trade-off principal: "fuzzy retorna **muitos** resultados; sem ranking, perde relevância". Hierarquia recomendada: **exact match > prefix match > fuzzy match**, com pesos diferentes.
**Aplicabilidade**: **SIM, valida estratégia**. Mesmo com Lunr.js de fallback, **rankear exact > fuzzy** evita poluição.
**Como adaptar**: na implementação de zero-result com Lunr fallback, sempre **prefixar resultados fuzzy com aviso visual** "Resultados aproximados:" para o usuário não confundir com hit exato.

### Exemplo 4.3 — TypeSense / Orama (alternativas — não verificadas)
**URLs tentadas**: https://typesense.org/docs/guide/, https://orama.dev/, https://oramasearch.com/ — todas falharam (ECONNREFUSED ou conteúdo errado: "orama.dev" agora é AI agent, não search).
**Aplicabilidade**: **NÃO RECOMENDO TROCAR** — Pagefind + Lunr fallback resolve, sem mudar stack (ADR-008 já confirmou). Trocar engine quebraria ADR-007.

### Conclusão Tema 4
- **Pagefind não tem fuzzy/sinônimos nativos** — proposta R2.1-B precisa ser refinada para "Pagefind + Lunr fallback + sinônimos via data-pagefind-meta + componente zero-result próprio".
- **Custo**: ~12-16h vs ~30h se trocar engine. Mantém ADR-007/008 intactos.

## Tema 5 — Export de citações em batch (Zotero, BibTeX)

### Exemplo 5.1 — Zotero "Exposing Metadata" (Highwire Press como padrão de fato)
**URL**: https://www.zotero.org/support/dev/exposing_metadata (verificado).
**Padrão observado**:
- Zotero connector reconhece **3 padrões abertos** em meta tags HTML: **Highwire Press** (`<meta name="citation_*">`), **Dublin Core** (`<meta name="DC.*">`), **COinS** (link/span com `class="Z3988"`).
- **Highwire é o padrão dominante** (Google Scholar, ACM, JSTOR, todos usam). É o que Zotero detecta automaticamente sem translator customizado.
- **Campos essenciais para catálogo de políticas (item type Report ou Document)**:
  - `citation_title` — nome do programa
  - `citation_author` — autor (pode ser instituição: "Brasil. Ministério da Educação")
  - `citation_publication_date` — ano de criação
  - `citation_publisher` — órgão responsável (ou "Catálogo de Políticas EJA + Inclusão Produtiva — FRM/IESP")
  - `citation_doi` — DOI Zenodo (ADR-007 prevê)
  - `citation_abstract` — resumo
  - `citation_language` — `pt-BR`
  - `citation_url` — URL canônica da ficha
- **Item type recomendado**: **`Report`** (Zotero suporta `citation_technical_report_institution` + `citation_technical_report_number`) ou **`Document`** se "Report" parecer formal demais.
**Aplicabilidade**: **SIM, valida R2.1-B (export RIS/BibTeX)** com refinamento poderoso:
- **Antes** de implementar export em batch, adicionar **5-7 meta tags Highwire Press no `<head>` de cada ficha**. Custo: 1-2h (template Eleventy injeta automaticamente). Resultado: Zotero connector (extensão browser) **detecta automaticamente** ao visitar qualquer `/politica/<slug>/` — usuário clica no ícone Zotero do browser, ficha vai pra biblioteca dele. **Sem nenhum botão custom no site.**
- Exportação em batch (R2.1-B propõe) é a **camada extra** para pesquisador-quantitativo (J7) que quer 30+ fichas sem clicar 30 vezes.
**Como adaptar**:
1. Sprint dedicado de 2h: injetar 7 meta tags Highwire em `_layouts/ficha.njk`.
2. Sprint dedicado de 12h: implementar checkbox "selecionar para exportar" + botão "Exportar X fichas (.bib | .ris | .csv)" client-side em `/buscar/`, `/explorar/`, `/uf/<uf>/`. JSON canônico já existe em `data/derived/`.

### Exemplo 5.2 — Schema.org Dataset + Report (riqueza adicional para crawlers)
**URL**: https://schema.org/Dataset (verificado).
**Padrão observado**: combinação **JSON-LD em `<head>`** com Schema.org `Dataset` (para o catálogo todo) + `Report` ou `GovernmentService` (para cada ficha). Propriedades essenciais: `name`, `description`, `url`, `creator/publisher`, `datePublished`, `license`, `spatialCoverage`, `temporalCoverage`, `keywords`. **Esses metadados também viram input para Google Dataset Search**, expandindo descoberta.
**Aplicabilidade**: **SIM, complementa R2.1-B**. Já estamos publicando JSON canônico (`data/derived/`); falta JSON-LD nas páginas. Custo: 3-4h.
**Como adaptar**: template Eleventy injeta JSON-LD em cada ficha + JSON-LD `Dataset` na Home + `/sobre/`.

### Conclusão Tema 5
- **Highwire Press meta tags + JSON-LD = baseline obrigatório** antes de export em batch.
- **Export em batch = camada premium** para persona acadêmica (J7).
- Custo total: ~17h (2 + 3 + 12). Resolve toda a J7 e melhora SEO em Google Dataset Search.

## Tema 6 — Onboarding e glossário em catálogos públicos

### Exemplo 6.1 — Datawrapper Academy (wiki por categoria, sem onboarding visual)
**URL**: https://www.datawrapper.de/academy (verificado parcialmente).
**Padrão observado**: Academy é **wiki estruturado por categoria** ("Bar Charts" 14 artigos, "Choropleth Maps" 18 artigos, etc.). **Não há tour interativo** ("Click here, then here"). Pedagógico: cada artigo é autônomo, com exemplos visuais inline, gif animados curtos, links cruzados. Modelo: "**docs por demanda**", não "tour".
**Aplicabilidade**: **REFINA R2.1-B**. A proposta "onboarding" deve ser **glossário + FAQ + exemplos destacados na Home + ficha-modelo**, não tour Shepherd.js:
- Tour interativo (Shepherd.js) é **overkill** — exige manutenção, fica desatualizado, atrapalha usuário recorrente, raramente é completado.
- **Glossário + FAQ + "comece por aqui" como página estática** é o padrão real.
**Como adaptar**:
- `/sobre/glossario/` com 30-50 termos definidos (EJA, qualificação profissional, transferência condicionada, esfera de execução, arranjo logístico-territorial, etc.).
- `/sobre/perguntas-frequentes/` com 10-15 Q&A.
- `/sobre/comece-por-aqui/` com 3 fluxos curados ("Sou técnico estadual" / "Sou pesquisador" / "Sou jornalista") + ficha-modelo destacada (PRONATEC).

### Exemplo 6.2 — Shepherd.js (avaliação de bundle e a11y)
**URL**: https://shepherdjs.dev/ (verificado).
**Padrão observado**: 14k stars no GitHub. Suporte completo a a11y (focus trap + ARIA + keyboard nav). Vanilla JS funciona (`new Shepherd.Tour()`). **Tamanho não documentado na home**, mas releases NPM mostram ~20-30kb gz.
**Aplicabilidade**: **PARCIAL**. Se decidir tour, Shepherd.js é a escolha técnica certa. **Mas R2.2 recomenda NÃO usar tour** — preferir glossário + FAQ + exemplos.
**Refina R2.1-B**: remover "onboarding via Shepherd.js" da lista; substituir por "página /sobre/comece-por-aqui/ + glossário inline".

### Exemplo 6.3 — Glossário inline com tooltip (padrão científico)
**URL**: implícito de R1.1-B + Wikipedia Manual of Style: Layout (já consultado em R1.2 mas com ângulo diferente).
**Padrão observado** (verificado por leitura cruzada de R1.2 + raciocínio): catálogos científicos sérios (Wikipedia, Scholar, MDN docs) usam **`<abbr title="...">`** ou **tooltip CSS-only** para definir termo na primeira menção. Não exige JavaScript pesado, é a11y-friendly.
**Aplicabilidade**: **SIM, valida R2.1-B (glossário)**.
**Como adaptar**:
- HTML semântico: `<abbr title="Educação de Jovens e Adultos">EJA</abbr>` em **toda primeira menção** de cada página (não toda menção).
- Hover/focus mostra tooltip nativo do browser.
- Para definição mais rica: classe `.term[data-term="EJA"]` que abre modal com definição + link "ver no glossário".
- Curadoria manual de 30-50 termos no schema.

### Conclusão Tema 6
- **Tour interativo (Shepherd.js) é overkill** para 8 wireframes — substituir por glossário inline + FAQ + página "Comece por aqui" + ficha-modelo destacada.
- **Glossário com `<abbr>` + tooltip CSS** é padrão a11y-friendly suficiente.
- Adicionar **3 fluxos curados por persona** na Home ou `/sobre/comece-por-aqui/` resolve onboarding cognitivo sem JS de tour.

## Aspectos extras

### Identidade brasileira sem clichê
- **Não usar verde-amarelo-azul (Pelé)** — Atlas Brasil PNUD usa, fica folclórico. Fiocruz, IBGE, gov.br novo evitam.
- **Usar 1 eixo cromático** + acentos sóbrios. Fiocruz = verde-floresta + cinzas mornos. IBGE = azul institucional + cinza. gov.br = azul-atlântico + Rawline. **R2.1-A Opção A está alinhada** (azul-IBGE + verde-floresta + sienna acento + papel).
- **Footer institucional rico** (logos + missão curta + ISSN/DOI + licença CC-BY) = padrão BR observado.
- **Fonte sóbria internacional** (IBM Plex) é mais "BR institucional moderno" do que **fonte brasileira recente** (BR Sonoma do gov.br DS) que prende visualmente ao governo federal.

### Custo real de Phosphor / Heroicons / Lucide
- **Phosphor** (https://github.com/phosphor-icons/web verificado): MIT, **6 pesos** (thin/light/regular/bold/fill/duotone), bundle completo ~3MB se webfont. Plugin Eleventy: `eleventy-plugin-phosphoricons` permite **inline SVG sob demanda** = só os 12-20 ícones usados, ~5-10kb total.
- **Lucide** (https://lucide.dev verificado): ISC, **1703 ícones**, tree-shakable nativo, vanilla JS suportado. ~8kb se 20 ícones.
- **Heroicons** (sabido por R1.2): MIT, par natural com Tailwind, 2 estilos (outline 1.5px, solid). ~5kb se 20 ícones.
- **Recomendação**: **Phosphor regular** se quer peso editorial; **Lucide** se quer leve técnico moderno; **Heroicons** se quer alinhar com Tailwind. Todos resolvem; importante é **escolher 1 e proibir os outros** (consistência > variedade).

### Glossário + jargão (vocabulários controlados PT-BR)
- **Não há tesauro UNESCO/OECD em PT-BR para política pública educacional** que seja canônico (verifiquei via WebSearch — só há Tesauro Brasileiro de Educação INEP, mas é incompleto para qualificação/inclusão produtiva).
- **Recomendação**: criar **vocabulário canônico próprio** (já existe `.claude/context/vocabulario-canonico.json`). Estender para incluir sinônimos populares + definições curtas (1 frase) por termo.
- Padrão "termo + tooltip + link 'saiba mais'": usar `<abbr title="...">` para sigla, `<span class="term" data-term="...">` para frase. Tooltip via CSS `:hover` + `:focus-within` = a11y friendly sem JS.

### Print stylesheets
- **R1.3 apontou ausência total de `@media print`**. Catálogos sérios (gov.uk, IBGE, Fiocruz) têm CSS print embutido.
- **Padrão mínimo**: ocultar header/footer/aside, ampliar fonte body para 12pt, remover backgrounds, mostrar URL completa após cada link (`a[href]:after { content: " (" attr(href) ")"; }`).
- **Ficha imprimível em 1-2 páginas A4** = entregável básico para gestor que quer arquivar versão impressa. ~4h de CSS.

### Mobile real em conexão BR
- Testar com Chrome DevTools throttle "Slow 3G" (400ms RTT, 400Kbps down). 
- Site Eleventy + Tailwind + Pagefind índice ~80kb deve carregar Home em **3-5s na primeira visita**, **<1s na segunda** (cache HTTP forte).
- **`/explorar/` com 7 cards + filtros**: o índice Pagefind começa em ~150kb (439 fichas, snippets curtos) — em 3G demora ~3s para ficar interativo.
- **Otimização principal**: **lazy-load do índice Pagefind** (só carregar quando usuário foca caixa de busca, não na carga inicial). Padrão: `pagefind.options.disableMainThread: true` + carregamento sob demanda.

## Anti-padrões observados (5 com fonte)

1. **Webfont com todos os pesos do Phosphor (~3MB)** — `phosphor-icons/web` README adverte. **Mitigação**: inline SVG via plugin Eleventy.
2. **Tour interativo Shepherd.js como onboarding obrigatório** — Datawrapper Academy escolheu wiki por algo. Tours são raramente completados, viram dívida de manutenção. **Mitigação**: glossário + FAQ + página "comece por aqui".
3. **Verde-amarelo-azul juntos como "identidade BR"** — Atlas Brasil PNUD usa e parece folclórico; Fiocruz, IBGE, gov.br novo evitam. **Mitigação**: 1 eixo cromático + acentos sóbrios.
4. **Heurística automática para classificar 439 fichas em eixos temáticos** — R2.1-B já apontou (30-40% erro), mas vale repetir: gov.uk DS Get Started usa **curadoria editorial humana**, não algoritmo. **Mitigação**: CSV override manual (~3-5h por todo o catálogo).
5. **Trocar engine de busca (Algolia, TypeSense, Orama) só porque Pagefind não tem fuzzy** — quebraria ADR-007. **Mitigação**: ADR-008 (Pagefind→Lunr fallback) já resolve com 12h vs 30h de troca.

## Notas de método

- **Pesquisa estendeu R1.2 sem repetir** — 0 fontes idênticas reusadas como fonte primária; quando uma URL aparece (Wikipedia Manual Style, gov.uk DS), foi com ângulo diferente (onboarding em vez de related nav, get-started em vez de tag, etc.).

- **Não recomendo trocar stack** — Eleventy/Tailwind/Pagefind/Lunr fallback resolvem com camadas de aplicação (meta tags, sinônimos via meta, componente zero-result próprio).
