# Schema v0.2 — adicionar info de snapshot

## Contexto

Schema v0.1 (Bloco A) já tinha `fonte_arquivo_path` (caminho do snapshot local), mas faltavam:

- **`fonte_sha256`**: hash SHA-256 do conteúdo bruto. Crítico para verificação de integridade ("o snapshot que tenho é o mesmo que foi originalmente capturado?") e para detectar mudanças entre revalidações periódicas.
- **`fonte_extensao`**: formato do snapshot (html/pdf/docx/doc/odt). Permite filtragem na UI ("mostrar só políticas com norma em PDF") e estatísticas de cobertura.
- **`fonte_ocr_aplicado`**: boolean indicando se o texto foi extraído via OCR (Tesseract+ocrmypdf). Sinaliza menor confiabilidade de extração para PDFs escaneados — útil tanto para QA quanto para mostrar ao usuário ("este texto pode ter erros de OCR").

Esses campos vinham sendo gerados pela skill `capturar-norma` v2.0 mas não cabiam no schema. Sem espaço no schema, o pipeline ETL não tinha onde colocar essa informação ao re-construir `policies-onda-1-*.json`.

## Alternativas consideradas

1. **Adicionar como opcionais (não-required)** ✅ ESCOLHIDO
   - Pro: 100% retrocompatível; fichas v0.1 sem esses campos validam contra v0.2
   - Pro: pode preencher só fichas cujo snapshot foi capturado
   - Con: nenhuma — único caminho razoável

2. **Adicionar como required**
   - Quebraria todas as 439 fichas atuais (não têm snapshot capturado quando geradas em C.1.g)
   - Pipeline precisaria capturar antes de validar — inverte ordem natural

3. **Embedar tudo em `fonte_arquivo_path` (string parseável)**
   - Tipo de gambiarra; sacrifica clareza por não-ter-que-mexer-no-schema
   - Hooks de validação ficam difíceis de implementar
   - Rejeitado

## Decisão

Adicionar 3 campos opcionais ao schema v0.2:

```json
"fonte_sha256":       { "type": ["string", "null"], "pattern": "^[a-f0-9]{64}$" },
"fonte_extensao":     { "enum": ["html", "pdf", "docx", "doc", "odt", "txt", "json", "xml", null] },
"fonte_ocr_aplicado": { "type": "boolean", "default": false }
```

Continuam todos opcionais (não em `required`). Schema v0.2 é **totalmente retrocompatível** com fichas v0.1.

## Justificativa

- **Integridade**: `fonte_sha256` é a base do versionamento sem sobrescrita (R5/R6 de captura-responsavel) e da detecção de mudança em revalidação periódica (D.5)
- **Filtragem**: `fonte_extensao` é necessário para UI/UX do site (filtros por tipo de documento) e para CI/CD (% de fichas com snapshot completo)
- **Qualidade**: `fonte_ocr_aplicado` é flag importante; OCR Tesseract pt em PDF escaneado tem ~95% precisão em textos limpos, ~70% em documentos antigos. Usuário precisa saber.
- **Retrocompatibilidade**: hooks `validate_json_schema.py` continuam funcionando sem mudança; testes integration_etl_completo.py continuam passando
- **Atualização incremental**: pipeline pode rodar `build_json.py` para preencher esses campos a partir de `data/external_snapshots/index.json` sem mexer no resto

## Trade-offs

- Schema cresce 3 campos (de ~50 para ~53). Nada drástico.
- Build_json.py precisa carregar `index.json` adicional. Trivial.
- Regra `dados-politicas.md` precisa documentar os novos campos (movendo-os de "Evoluções planejadas" para campos atuais). Edição em D.4.
